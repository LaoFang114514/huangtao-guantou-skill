# 编码约定

跨语言的通用约定；项目自身规范优先。

## 命名

- 文件与目录：小写 + 连字符或下划线，跟随项目现有习惯，不混用。
- 变量与函数：表达意图而非类型（`elapsed_ms` 优于 `num`）。
- 布尔值：`is_` / `has_` / `can_` 前缀。
- 常量：全大写 + 下划线；魔法数字一律提取命名。
- 缩写保持团队共识，不新造缩写。

## 结构

- 单文件只承担一类职责；超过约 400 行考虑拆分。
- 依赖方向单向：上层调用下层，禁止反向引用与循环依赖。
- 公共工具放 `utils` / `shared`，但同一功能不要出现两套实现。
- 入口文件只做编排，不写业务细节。

## 错误处理

- 不吞异常：捕获后要么处理，要么补充上下文再抛出。
- 失败信息包含：做什么、输入是什么、期望与实际。
- 区分可恢复与不可恢复错误；不可恢复时快速失败（fail fast）。
- 资源释放使用语言对应机制（`defer` / `with` / `try-with-resources`）。

## 日志

- 级别固定：`debug` 细节、`info` 关键流程、`warn` 可恢复异常、`error` 失败。
- 结构化字段优先于拼接字符串。
- 不记录密钥、令牌、完整个人敏感信息。
- 提交前清理调试输出。

## 配置

- 环境相关参数走环境变量或配置文件，禁止硬编码地址、账号、路径。
- 提供 `.env.example`，不提交真实 `.env`。
- 默认值必须安全（默认只读、默认关闭）。

## 依赖与版本

- 新增依赖前确认现有依赖能否满足。
- 锁文件必须与清单同步提交。
- 升级依赖单独提交，便于回滚。

## 提交信息

```
<type>(<scope>): <摘要>

- 说明动机与行为变化
- 说明影响面与验证方式
```

`type` 使用 `feat` / `fix` / `refactor` / `docs` / `test` / `chore`。

## 评审自查

- [ ] 改动范围与任务一致，无无关文件
- [ ] 命名与项目风格一致
- [ ] 异常路径有处理
- [ ] 无调试残留与硬编码密钥
- [ ] 文档、配置、示例同步
