# 工作流详解

适用于任意语言与技术栈的改动类任务。核心是「先摸底、再动手、留验证」。

## 1. 摸底（Read before write）

1. 用 `scripts/project_scan.py` 看目录职责、语言分布、清单文件。
2. 读根目录 README、包管理清单、构建脚本，确认：
   - 语言与运行时版本
   - 包管理器与锁文件（不要混用 npm / pnpm / yarn）
   - 启动、构建、测试、lint 命令
3. 读同类模块的现有实现，确认命名、分层、错误处理习惯。

## 2. 定方案

- 列出改动点：文件、函数、接口、数据结构。
- 列出影响面：调用方、配置、迁移脚本、文档。
- 列出验证方式：单测、构建、手工复现步骤。
- 有多个可行方案时，先说明取舍再动手；只给结论不给理由视为未完成。

## 3. 实现

- 最小可用优先：先让主路径跑通，再加边界处理。
- 保持既有风格：缩进、命名、目录结构跟随项目，不引入新范式。
- 不做顺手重构：无关文件的格式化、重排、改名一律避免。
- 新依赖必须说明必要性，并确认锁文件同步更新。

## 4. 验证

- 优先跑项目自带命令，而不是自造脚本。
- 至少覆盖：正常路径 + 一个异常路径。
- 验证失败时先定位假设错在哪，不连续盲改；同一错误重试不超过两次。

## 5. 交付

- 跑 `scripts/check_delivery.py`，处理 FAIL 项。
- 输出：改了什么、为什么、怎么验证、已知限制。
- 涉及数据或接口变更时，写明回滚方式。

## 常见偏差

| 偏差 | 后果 | 纠正 |
| --- | --- | --- |
| 没读代码直接改 | 破坏隐式约定 | 先 grep 调用方 |
| 顺手格式化 | diff 变大难审 | 只改目标行 |
| 盲改试错 | 引入新问题 | 回到假设验证 |
| 不跑构建 | 交付即失败 | 交付前执行一次 |
